# memo. デザインシステム

## このドキュメントの役割

メモアプリ全体の見た目と操作体験を統一するための基準。機能やページを追加する際は、ここに記載した共通部品とスタイルを起点に実装する。
Apple の Human Interface Guidelines を参考にした、余白のある落ち着いたデザインを目指す。Apple 製 UI の完全な再現や、適合性を認証したものではない。

「現状」は実装済みの仕様、「追加時のルール」は今後の実装に適用する方針を示す。未実装の部品を利用可能なものとして扱わない。
ユーザーから明示的なデザイン変更があった場合は、その依頼に沿って共通実装と本書を一緒に更新する。

## 基準となる実装

パスはリポジトリルートを基準とする。

| 対象 | 参照先 | 役割 |
| --- | --- | --- |
| 共通スタイル | [app/globals.css](../app/globals.css) | 色、書体、レイアウト、画面幅への対応、ダークモード |
| アプリ共通枠 | [components/layout/app-shell.tsx](../components/layout/app-shell.tsx) | ヘッダー、サイドバー、モバイルナビゲーション、本文、フッター |
| 共通枠の適用 | [app/layout.tsx](../app/layout.tsx) | 日本語設定、メタデータ、AppShell の配置 |
| 基準ページ | [app/page.tsx](../app/page.tsx) | ページ見出し、案内パネル、メモ・カテゴリ・タグの空状態 |
| 表示・操作のテスト | [__tests__/app-shell.test.tsx](../__tests__/app-shell.test.tsx)、[__tests__/page.test.tsx](../__tests__/page.test.tsx) | ランドマーク、ナビゲーション、空状態の確認 |

本書と実装の不一致に気づいた場合は、既存画面と変更の意図を確認し、依頼の範囲で整合させる。ページ内の個別上書きで不一致を隠さない。

## デザインの基本方針

- 白、温かみのあるグレー、落ち着いたグリーンを基本に、内容を読みやすく配置する。
- 高級感は余白、整列、文字の階層、控えめな境界線で表現する。強い影や派手な装飾を標準にしない。
- 同じ意味・同じ操作には同じ名称、色、形状、アイコンを使う。
- ページごとにブランド、フォント、主要な配色、ナビゲーションの位置を変えない。
- 装飾よりも読みやすさと操作の分かりやすさを優先する。

## 色

色の実装上の定義元は `app/globals.css` の CSS カスタムプロパティ。UI には役割に合う `var(--...)` を使い、ページごとに似た色を直接定義しない。

| トークン | 用途 | ライト | ダーク |
| --- | --- | --- | --- |
| `--background` | アプリ背景 | `#fdfdfb` | `#191c19` |
| `--foreground` | 主な文字 | `#292e2b` | `#e7eae3` |
| `--sidebar` | サイドバー・補助領域 | `#f5f6f3` | `#1e221e` |
| `--surface` | カード・入力面 | `#ffffff` | `#202420` |
| `--muted` | 補助文字 | `#70766f` | `#a2ac9f` |
| `--border` | 境界線 | `#e7eae3` | `#343b33` |
| `--accent` | アクセント・選択中・フォーカス | `#35654b` | `#a8c9a9` |
| `--accent-soft` | 選択中などの薄い背景 | `#e6ede4` | `#303e32` |
| `--hero` | トップページの案内パネル | `#edf1e8` | `#283227` |
| `--header` | 半透明ヘッダー | `rgb(253 253 251 / 92%)` | `rgb(25 28 25 / 94%)` |

現状の紙のイラストには装飾専用の直接指定色がある。これらを通常の操作 UI の配色として流用しない。
成功・警告・エラー・削除用の共通色は未定義。必要になった時点で、役割名を付けた共通トークンとライト／ダーク両方の値を追加する。アクセントをボタン背景へ使う場合も、文字との組み合わせを両テーマで確認する。

## 文字とアイコン

### 現状

- UI の書体は `--system-font`。OS のシステムフォントと日本語フォールバックを使用する。
- `body` は 14px。ページの主見出しは 29px、760px 以下では 26px。
- セクション見出しは主に 14px、説明は主に 12〜13px、件数などの補助表示は主に 11〜12px。
- トップの案内見出しは 25〜35px の可変サイズ。紙のイラスト内には専用書体と小さな装飾文字がある。
- アイコンライブラリは `lucide-react`。ナビゲーションやセクションのアイコンは主に 19〜21px、線幅は主に 1.5〜1.65。

### 追加時のルール

- 操作名や本文を装飾文字のサイズに合わせて小さくしない。長文メモやフォームは用途に応じて読みやすいサイズ・行間を共通定義する。
- 文字の階層はサイズ・太さ・余白で表現し、全てを太字にしない。原則としてページの主見出しは `h1` を一つ配置する。
- 同じ用途の文字は既存スタイルを再利用する。新たな書体の導入は共通方針の変更として扱う。
- 同じ役割のアイコンは同じ種類・大きさ・線幅で揃える。絵文字や別のアイコンセットを操作アイコンに混在させない。
- 装飾アイコンは `aria-hidden="true"`、アイコンだけの操作には日本語のアクセシブルな名前を付ける。

## レイアウト・余白・形状

### 現状の基準値

| 項目 | 実装値 |
| --- | --- |
| ヘッダーの高さ | 通常 80px、760px 以下で 68px |
| サイドバーの幅 | 通常 244px、1100px 以下で 212px |
| モバイルナビゲーション | 760px 以下で開閉式へ切り替え。開くとヘッダーの下に表示 |
| ページ幅 | `.home-content` の最大幅 1180px。内側余白を含む |
| ページの左右余白 | 通常 52px、1100px 以下 30px、760px 以下 22px、520px 以下 18px |
| 通常のカード | 1px の境界線、角丸 14px |
| トップの案内パネル | 角丸 18px |
| ナビゲーション項目 | 角丸 9px、最小高さ 46px |
| モバイルのメニューボタン | 44 × 44px、角丸 10px |
| カテゴリ・タグの配置 | 通常 2 列、520px 以下で 1 列 |

余白と角丸は現在、各共通 CSS クラスに定義されており、共通トークンへの抽出は未実施。
新しいページでは既存の見出し・カード・ページ余白に合わせる。繰り返し使う値を変更・追加するときは共通クラスまたは役割を持つトークンへまとめ、既存の利用箇所も揃える。

トップページの案内パネルと紙のイラストは、そのページ固有の装飾。編集・一覧・認証など全ページに同じ案内パネルを置く必要はない。

## 共通部品の使い方

### 実装済み

- `AppShell` は `app/layout.tsx` で一度だけ適用する。各ページにヘッダーやサイドバーをコピーせず、二重にラップしない。
- `AppShell` が `main` を提供するため、ページ内にさらに `main` を作らない。
- `.home-content`、`.page-heading`、`.title-row`、`.section-heading`、`.organize-panel`、`.empty-notes` などは既存 CSS のパターン。独立した React コンポーネントとしては未抽出。
- ナビゲーションの現在地は `aria-current` と共通スタイルで示す。現状のリンクはトップページ内のセクションを参照している。

### 部品・ページを追加するとき

1. 既存の部品と CSS に同じ役割がないか確認する。
2. 存在する場合は再利用し、差異は共通部品の明示的なバリエーションで表す。
3. 同じ構造を複数画面で使う場合は、必要な時点で共通部品へ抽出する。共通 UI 部品は `components/ui/`、レイアウト部品は `components/layout/` を配置先の基準にする。`components/ui/` は現時点で未作成。
4. ページ固有 CSS はその機能の内容に限定する。共通部品をページ固有セレクターや `!important` で別の見た目に変えない。
5. 共通部品やトークンの変更時は既存の利用画面も確認し、本書を更新する。

ボタン、フォーム入力、ダイアログ、通知、Markdown 表示部品は未実装。導入時に共通の外観と状態を定義し、後続画面から再利用する。
新たな UI ライブラリの既定テーマをそのまま混在させず、本アプリの色・書体・角丸・操作状態に合わせる。

認証ページなどでナビゲーションのない構成が必要な場合は、レイアウトの責務を分けて構成する。その場合もブランド・共通 UI のスタイルは維持する。
独立ページを追加した場合は、パンくずと現在地表示をページに合わせて更新する。現在の固定表示やハッシュ判定をそのまま流用しない。

## 操作・状態・文章

- 移動はリンク、状態を変える操作はボタンにする。フォームの項目には見えるラベルを付ける。
- 通常、ホバー、フォーカス、選択中、無効、処理中、エラーのうち必要な状態を共通部品で揃える。
- 読み込み中、データがない状態、検索結果がない状態、取得失敗を区別する。取得失敗を「0 件」として表示しない。
- 未実装の操作を動くように見せず、保存・認証・同期が成功していない状態を成功と表示しない。
- 操作の表記は「メモ」「カテゴリ」「タグ」など既存の日本語に統一する。API や内部実装の説明を操作 UI に持ち込まない。
- Markdown の見出し、本文、リスト、引用、リンク、コードなどの外観は、表示部品の範囲に共通定義する。グローバルな `h1` やリンクの上書きでアプリの見出し・ナビゲーションを変えない。

## 画面幅・テーマ・アクセシビリティ

- 既存の 1100px、760px、520px のブレークポイントを基準にする。新たな境界が必要な場合は目的を明確にし、同じ部品内で統一する。
- ダークモードは現在 `prefers-color-scheme` に追従する。ページごとに独立したテーマ判定を追加しない。
- 内容が長い場合も横にはみ出さない構成にする。Markdown のコードや表など、必要な横スクロールは内容の領域内に収める。
- 小さなアイコンでも操作領域は原則 44px 四方以上を確保する。既存の装飾アイコンの表示サイズと操作領域を混同しない。
- `:focus-visible`、本文スキップリンク、Esc による閉じる操作とフォーカス復帰を維持する。新しい開閉 UI でもキーボードから操作可能にする。
- 色だけで状態を伝えず、文字や形状も併用する。両テーマで文字と背景のコントラストを確認する。
- `prefers-reduced-motion` を尊重する。読みやすさのための文字拡大を妨げない。

## 変更時の確認手順

1. 作業開始時に本書を読み、変更に関係する実装ファイルを確認する。
2. 再利用する共通部品・スタイルと、新しく必要な部品を整理して実装する。
3. UI 変更時は実ブラウザで既存トップページと変更した画面を見比べる。少なくとも PC（例: 1440px）、モバイル（例: 390px）、狭い幅（320px）を確認し、変更したブレークポイントの前後も確認する。
4. ライト／ダーク、長い文字、キーボード操作、関連する読み込み・空・エラー状態を確認する。必要に応じて文字拡大と動きを減らす設定も確認する。
5. 共通仕様を変更・追加した場合は本書を同じタスクで更新する。新しい値を表へ追加するときは、実装にも存在することを確かめる。
6. AGENTS.md のテスト・型チェック・lint のルールに従い、確認結果と未確認事項を報告する。自動テストの成功だけで見た目の統一を確認済みとしない。

この手順は毎回のデザイン再承認を求めるものではない。既存の基準内での追加はそのまま進め、明示されたユーザーの変更依頼を優先する。
